--- title: JWT Decoder & Verifier (JSON Web Tokens) description: Decode a JWT's header and payload, see exp, nbf and iat as dates, and verify HS256, RS256, PS256, ES256 or EdDSA signatures privately in your browser. category: Developer keywords: [jwt decoder, decode jwt, jwt verifier, verify jwt signature, json web token decoder, jwt parser, jwt debugger, jwt expiration checker] howto: | ## How to use the JWT decoder Paste a token into the box. It may start with `Bearer ` or be split over several lines; both are cleaned up. The header and payload appear as formatted JSON, and the claims table shows `exp`, `nbf` and `iat` as dates in UTC and in your time zone, with a badge saying whether the token is valid right now. To check the signature, enter the key under **Verify the signature**. The field changes with the algorithm named in the token's header: | Algorithm | Signed with | Verify with | |---|---|---| | HS256, HS384, HS512 | Shared secret (HMAC) | The same secret, as text or Base64 | | RS256, RS384, RS512 | RSA private key (PKCS #1 v1.5) | RSA public key | | PS256, PS384, PS512 | RSA private key (PSS) | RSA public key | | ES256, ES384, ES512 | EC private key (P-256, P-384, P-521) | EC public key | | EdDSA | Ed25519 private key | Ed25519 public key | A public key can be PEM (`BEGIN PUBLIC KEY`, `BEGIN RSA PUBLIC KEY` or a `BEGIN CERTIFICATE` certificate), a single JWK, or a whole JWKS as served at an identity provider's `jwks_uri`. From a JWKS, the key whose `kid` matches the token's header is used. ## What is inside a JWT A JWT (RFC 7519) in compact form is three Base64url strings joined by dots: a header, a payload of claims, and a signature. Base64url is an encoding, not encryption. Anyone holding the token can read the payload, so it must never contain secrets. The signature covers the exact characters of `header.payload`, which is why changing a single character of either part makes verification fail. The registered claims have short names: `iss` (issuer), `sub` (subject), `aud` (audience), `exp` (expiry), `nbf` (not before), `iat` (issued at) and `jti` (token ID). The three time claims are NumericDate values, counted in seconds since 1970-01-01 UTC. A 13-digit value is in milliseconds, a common bug, and the page warns when it sees one. ## How verification works here Signatures are checked with the browser's Web Crypto API (`crypto.subtle.verify`) as RFC 7518 defines the algorithms: HMAC for HS, RSASSA-PKCS1-v1_5 for RS, RSASSA-PSS with a salt as long as the hash for PS, and ECDSA with the raw R‖S signature (64, 96 or 132 bytes) for ES. EdDSA follows RFC 8037. The token and key stay in this tab. ## Security notes - **`alg: none`** marks an unsigned token. Anyone can write one, so a server must never accept it. Some JWT libraries once did, which let attackers forge any claims they liked. - **Algorithm confusion.** A server that trusts the `alg` in the header can be tricked into using its RSA public key as an HMAC secret. Configure the expected algorithm on the server instead of reading it from the token. - **Short HMAC secrets** can be guessed offline from a single token. RFC 7518 requires a key at least as long as the hash: 32 bytes for HS256. - A valid signature proves who issued the token, not that it is meant for you. Servers must also check `exp`, `nbf`, `iss` and `aud`. faq: - q: Is my token sent to a server? a: No. Decoding and signature checks run entirely in your browser with JavaScript and the Web Crypto API. The token, secret and keys are never uploaded or stored, so it is safe to inspect real tokens here. - q: Can anyone read the contents of my JWT? a: Yes. The header and payload are only Base64url-encoded, not encrypted, so anyone who has the token can decode them. Keep secrets out of the payload, or use an encrypted JWE token. - q: Why does verification fail even though the secret is right? a: Check whether the secret is stored Base64-encoded (tick "Secret is Base64 encoded"), that no spaces or line breaks were copied with it, and that the whole token was pasted. Any change to the header or payload also breaks the signature. - q: Where do I get the public key for a provider's tokens? a: Identity providers publish their keys as a JWKS. Open the provider's `/.well-known/openid-configuration`, follow the `jwks_uri` link and paste the JSON here; the key matching the token's `kid` is picked automatically. - q: Does a verified signature mean I can trust the token? a: Only partly. It proves the token was signed with that key and not changed since. Your application must also check the expiry, the issuer and the audience before accepting it. ---
